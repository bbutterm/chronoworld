# Тесты

Все тесты — Vitest (`tests/**/*.test.ts`), запускаются `npm test`; `npm run check` = `content:check` + `typecheck` + `npm test`.
Тесты работают с настоящими данными из `data/` через `scripts/lib/content-node.ts` (`loadContent`, `loadGameContext`, `loadFullContext`)
или с маленьким контентом из `tests/helpers.ts` (`content`, `unitDef`, `skill`).

## Что проверяется

| Файл | Что |
| --- | --- |
| `battle.test.ts`, `battle-edge.test.ts` | детерминизм боя, конец боя, крайние случаи (пустые отряды, статусы, движение) |
| `targeting.test.ts`, `formulas.test.ts` | выбор целей, формулы урона и лечения, `Rng` |
| `content.test.ts`, `context.test.ts`, `jobs.test.ts` | схемы контента, сборка полного контекста (`buildGameContext`), профессии |
| `progression.test.ts`, `campaign.test.ts`, `chapters.test.ts`, `offline.test.ts` | статы и навыки героев, опыт, кампания, офлайн-сундук |
| `save.test.ts` (+ `tests/fixtures/save-v*.json`) | сохранение, миграции старых версий, битые сохранения |

Общие инварианты фазз-тестов — `tests/invariants.ts` (`battleProblems`, `saveProblems`, `RULE_ERRORS`). Их можно
вызывать и из обычных тестов: функции возвращают список нарушений, пустой — всё хорошо.

## Фазз-тесты (Q)

Вся случайность — только из `Rng` проекта (никакого `Math.random`), поэтому один seed полностью задаёт прогон.
По умолчанию seed фиксированы — тесты детерминированы и быстрые (все три фазза вместе — около 2–3 с).

### Бои — `tests/fuzz-battle.test.ts`

320 боёв. Отряды: герои всех профессий на случайных уровнях (с историей профессий по веткам) и случайной
экипировкой, монстры со случайным множителем статов, юниты из `data/units` по id, враги случайного этапа
кампании или этажа башни; случайные пустые слоты, иногда пустой отряд целиком. Иногда укорочен лимит времени
или изменён тик — чтобы чаще проверять таймаут.

Инварианты (`battleProblems`):

- ровно одно событие `end`, оно последнее; `winner`, `reason`, `duration` совпадают с результатом;
- время событий не убывает, не больше `timeLimitSeconds`; `duration ≤ timeLimitSeconds`;
- нет `NaN`/`Infinity` ни в одном числовом поле лога, отчёта и снимков юнитов;
- `hp` в событиях `damage`/`heal` в `[0; maxHp]`, щит ≥ 0, энергия в `[0; energy.max]`;
- мёртвый юнит не ходит, не двигается, не бьёт, не лечит, не накладывает статусы, не получает урон и не умирает
  повторно (доигрывать может только урон за ход (`dot`) от его статуса на живом враге);
- `wipe` — у проигравшей стороны все мертвы; отчёт `alive` совпадает с логом;
- детерминизм: тот же seed → тот же результат (побайтно); `log: false` не меняет итог.

### Прогрессия и сохранение — `tests/fuzz-progression.test.ts`

50 прогонов × 100 шагов. Старт — новая игра или «ветеран» (прокачанные герои, часть кампании, гемы, предметы).
Шаги — случайные действия с весами: `actPlayStage`, `actSkipStage`, `actClaimOffline` со скачками часов вперёд
(в том числе дальше лимита сундука) и назад, `actUseFastRewards`, `actChangeJob`, `actEquip`/`actUnequip`,
`actClimbTower`, экспедиции (`startExpedition` с автоподбором и случайной группой, `claimExpedition`), `claimQuest`,
`claimActivity`, `claimAchievement`, пресеты (`savePreset`, `applyPreset`, `deletePreset`), `autoFormation`,
перестановка отряда, смена дня (вперёд и назад), `serialize → deserialize`. Часть аргументов намеренно
неверна (неизвестный герой/предмет/этап, неверное число героев, пустое имя пресета…).

После каждого шага (`saveProblems`):

- `SaveStateSchema.parse` проходит, `deserialize(serialize(save))` даёт то же самое;
- ресурсы — неотрицательные целые; отряд — 5 слотов, существующие неповторяющиеся герои;
- уровень героя ≤ максимума профессии, опыт не «застрял» ниже порога уровня;
- предметы: id уникальны, описания существуют, надеты на существующих героев, на герое ≤ 1 предмета в слоте;
- кампания, башня, экспедиции (герой — максимум в одной, одна на локацию, мощь не ниже порога), пресеты, полученные награды — без повторов и в лимитах.

Кроме того:

- входной `save` глубоко заморожен (`deepFreeze`) — функция, которая меняет его на месте, упадёт с `TypeError`;
- допустимы только ошибки правил: `GameRuleError`, `FeatureError`, `EquipmentError`, `TowerError`, `MetaError`
  (`RULE_ERRORS`); любое другое исключение — баг; после ошибки правил `save` не меняется;
- тест проверяет, что ключевые действия хотя бы раз выполнились успешно (фазз не упирается только в ошибки).

Третий тест в том же файле — **испорченные сохранения** (300 шт.): сохранение после нескольких действий портится
(удалённые ключи, чужие типы, странные числа, обрезанный JSON, старая версия формата для миграций).
`deserialize` должен бросать только `SaveError`, `loadOrNew` — не бросать и вернуть `source: 'reset'`;
если испорченное сохранение всё же прошло схему, случайные действия над ним бросают только ошибки правил.

## Как воспроизвести падение фазза

Сообщение об ошибке содержит seed, например:

```
seed 3795 (FUZZ_SEED=3795):
  #181 t=4.6 damage: мёртвый B1 наносит урон
```

Для прогрессии — ещё шаг, действие, день и последние 15 действий («путь»).

Повторить только этот случай:

```bash
FUZZ_SEED=3795 npx vitest run tests/fuzz-battle.test.ts
FUZZ_SEED=3795 FUZZ_VERBOSE=1 npx vitest run tests/fuzz-battle.test.ts --silent=false   # + события лога вокруг нарушения
FUZZ_SEED=1017 npx vitest run tests/fuzz-progression.test.ts -t "прогрессии"
FUZZ_SEED=12,40,77 npx vitest run tests/fuzz-*.test.ts                                   # несколько seed через запятую
```

Переменные окружения:

| Переменная | Что делает |
| --- | --- |
| `FUZZ_SEED` | прогнать только эти seed (через запятую) |
| `FUZZ_RUNS` | сколько seed подряд прогнать вместо стандартного числа (долгий прогон: `FUZZ_RUNS=20000`) |
| `FUZZ_STEPS` | шагов в одном прогоне прогрессии (по умолчанию 100) |
| `FUZZ_VERBOSE` | печатать подробности (лог вокруг нарушения, статистику действий); нужен `--silent=false` |

Нашли баг — исправьте его и добавьте обычный (не фазз) регрессионный тест с минимальным примером, как
«регрессия: погибший от контратаки…» в `fuzz-battle.test.ts`. Seed фазза в тексте теста — для истории.

Генераторы используют порядок данных из `data/` (сортировка по id), поэтому после изменения контента тот же
seed может дать другой бой — для воспроизведения старого падения откатите данные к тому коммиту.
