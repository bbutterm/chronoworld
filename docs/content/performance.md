# Производительность: загрузка (`npm run perf:load`) и бой (`npm run perf`)

Цель — Telegram Mini App на слабом Android (WebView, 2–3 ГБ ОЗУ, мобильный GPU уровня Mali/Adreno 5xx).
Здесь — как меряем, что было, что сделано и что осталось сделать.

## Как меряем

`scripts/perf.mjs` устроен как e2e: сам поднимает vite (порт `PERF_PORT`, по умолчанию 5185), берёт
глобальный Playwright (`npm root -g`) и уже скачанный Chromium, ничего не устанавливает.

1. Чистый `localStorage`, скорость боя 2x.
2. CPU замедлен в 4 раза (`Emulation.setCPUThrottlingRate`, `PERF_CPU`) — грубая модель слабого телефона.
3. Подряд `PERF_RUNS` (5) одинаковых тестовых боёв (seed 7, отряды `data/phase0.json`, ~34 с боя → ~17 с на 2x).
4. В каждом бою собирается:
   - интервал кадров по `requestAnimationFrame` (среднее, p95, число кадров > 50 мс);
   - **шаг Phaser** — время от `prestep` до `postrender` (update + подготовка отрисовки, чистый JS);
   - **время JS за бой** — `ScriptDuration` из CDP `Performance.getMetrics`;
   - раз в 250 мс: число объектов сцены (с вложенными в контейнеры), из них `Text`, активные твины и таймеры;
   - сколько за бой **создано** игровых объектов (`addedtoscene`), твинов и таймеров Phaser;
   - после боя (после принудительной сборки мусора): куча JS, число живых экземпляров
     `Text/Image/Sprite/Container` во всей игре (CDP `queryObjects`) и сколько из них уже уничтожены,
     но удерживаются ссылками.
5. Текстуры: все загруженные, размер = w×h×4 байт (так они лежат в памяти GPU), отдельно листы юнитов
   `spr_*` и те, что реально нужны этому бою; до боёв и после — память текстур по экранам (главная, герои,
   карточка героя, бой, главная после боёв).

Скрипт **падает**, если: ошибка в консоли; растёт число слушателей на долгоживущих эмиттерах
(игра, масштаб, текстуры, анимации, ввод, события сцены боя); после выхода из боя в сцене остались
объекты/твины/таймеры; растёт число текстур или анимаций; куча выросла больше чем на `PERF_HEAP_LEAK_MB`
(8 МБ) между 2-м и последним боем; растёт число живых игровых объектов от боя к бою.

Переменные: `PERF_PORT`, `PERF_RUNS`, `PERF_CPU`, `PERF_SEED`, `PERF_HEAP_LEAK_MB`, `PERF_JSON=файл` (сырые цифры),
`PERF_SNAPSHOT=файл` (снимок кучи после боёв — искать, кто держит объекты).

**Оговорка про кадры.** В headless Chromium WebGL рисуется программно (SwiftShader), поэтому интервал
кадров ~200 мс определяется растеризацией на CPU, а не нашим кодом: даже главный экран без боя даёт
~120 мс на кадр. Для оценки кода смотрите «шаг Phaser» и «время JS за бой». Интервал кадров полезен
как грубая мера заливки (fill rate) — см. раздел «Отрисовка».

## Что сделано

Всё в `src/game/scenes/BattleScene.ts`, `src/game/battleFx.ts`, `src/game/perf.ts`; вид боя не менялся
(те же длительности, кривые, слои, столбики цифр, золотые цифры ульты, след HP).

- **Пулы** (`Pool` в `perf.ts`) вместо create/destroy: цифры урона и подписи статусов (`Text`), вспышки попаданий
  и снаряды (`Image`), свечение под кастером ульты (`Ellipse`). Раньше каждый удар создавал и уничтожал `Text`
  (новый canvas + WebGL-текстура + замер шрифта) и `Image`.
- **Плашка ульты** строится один раз на сторону и переиспользуется (ульт за тестовый бой ~60 — было ~60 контейнеров,
  120 прямоугольников и 120 `Text`).
- **Без твина на каждое событие**: цифры, подписи, вспышки, снаряды (`FloatLayer` в `battleFx.ts`), белый след HP и
  красный оттенок попадания анимируются в `update()` сцены по времени боя (с учётом скорости), с теми же кривыми
  (`Quad.easeOut`, `Quad.easeIn`, `Back.easeOut`). Записи анимаций тоже переиспользуются.
- **Своя очередь отложенных действий** (`Scheduler`) вместо `time.delayedCall` на каждый удар/снаряд: без `TimerEvent`
  на событие, тот же порядок и отсчёт со следующего шага, как у часов Phaser.
- **Лимит надписей**: не больше `MAX_FLOATS` = 24 на экране; при переполнении первой уходит самая старая
  (в тестовом бою на 2x одновременно бывает до ~27 всех `Text` вместе с неподвижными — лимит почти не срабатывает).
- **Кэш стилей текста** (`TextStyleCache`): один объект стиля на сочетание параметров и один замер шрифта на размер —
  Phaser не сканирует пиксели (`MeasureText`) для каждой новой цифры; стиль применяется без лишней перерисовки,
  затем один `updateText`.
- **Таймер боя** перерисовывается раз в секунду, а не строка + форматирование каждый кадр.
- **Анимации**: один слушатель `animationcomplete` на юнита (раньше `once` на каждую атаку/получение урона —
  прерванные анимации оставляли висящих слушателей). У юнита без листа смерти стойка после смерти останавливается.
  Анимация смерти из листа не повторяется и сама останавливается на последнем кадре.
- **Выключение сцены**: по `shutdown` (`once` — без накопления слушателей) сцена забывает юнитов, пулы, очередь и плашки,
  и уничтоженные объекты прошлого боя сразу доступны сборщику мусора.

Проверка: `tests/game-perf.test.ts` (пул, очередь, кэш стилей, кривые как у Phaser), `npm run perf` (утечки), `npm run e2e`.

Ниже — исторический текст пакета U. Остальные ~14 МБ — UI: фон арены 1080×1920 (7.9 МБ), атлас Kenney, иконки, портреты. 0.2 МБ «листов» — силуэты-заглушки
128×128 для спрайтов без арта. Шаг Phaser и время JS за бой не изменились (9.8 / 17.6 мс, 1.22 с).

Как устроено (`src/game/sprites.ts`, `src/game/spriteCache.ts`):

- **Старт** (`BootScene`): UI из манифеста, файлы портретов (64×64) и силуэты для спрайтов без арта. Затем портреты
  героев игрока («малый набор»): их листы грузятся по одному и сразу выгружаются.
- **Листы по требованию**: `whenSprites(scene, ids, ready)` / `ensureSprites(scene, ids): Promise` — грузит недостающие
  листы, создаёт анимации и держит листы, пока сцена не выключится. Всё уже в памяти — `ready` вызывается сразу, в том
  же кадре (без мигания). Грузится дольше 150 мс — поверх сцены «Загрузка…». Листы грузятся через `Image` +
  `textures.addSpriteSheet`, а не загрузчиком сцены: загрузчик сбрасывается при выключении сцены, а лист нужен и следующей.
  Не загрузился — силуэт-заглушка и `console.warn`, как раньше.
- **Кто грузит**: бой (листы только своих юнитов; до загрузки часы боя стоят, `BattleScene.ready`), карточка героя
  (лист текущей профессии), экран тестового отряда (листы в слотах).
- **LRU с бюджетом** `SHEET_BUDGET_BYTES` = 32 МБ (было 60, P12) (оценка w×h×4): после выключения сцены её листы остаются в кэше,
  сверх бюджета выгружаются самые давние неудерживаемые (`anims.remove` для всех анимаций листа + `textures.remove`).
  Переходы «карточка героя ↔ бой ↔ итоги» не перезагружают листы. Листы, которые держит активная сцена, не
  выгружаются, даже если бюджет превышен (бой с 6 старыми листами RO + босс ≈ 80 МБ).
- **Портреты** генерируются один раз на спрайт из кадра стойки в канвас до 160×160 (≈100 КБ) и остаются навсегда.
  Экраны-списки (герои, отряд, этап, башня, поручения, смена профессии, итоги) листов не держат: `portrait()` в
  `screen.ts` показывает нейтральный силуэт, а `requestPortrait` по одному грузит лист, вырезает портрет и сразу
  выгружает лист, если его не держит сцена. Портрет подменяется на месте.
- Для e2e/perf в dev-сборке: `window.__sprites.busy()` (идёт загрузка), `window.__sprites.stats()` (что в кэше).

## Загрузка и размер сборки (пакет «телефон», 2026-09-27)

### Как меряем загрузку

`npm run perf:load` (`scripts/perf-load.mjs`, порт `LOAD_PORT` = 5190): `vite build` → `vite preview` → Chromium 360×640 @2,
CPU ×4 (`LOAD_CPU`), сеть «Fast 3G» как в DevTools (RTT 562.5 мс, 180 000 Б/с вниз; `LOAD_NET=none` — без сети), кэш
выключен. Метки ставит `src/main.ts`: `cw:boot-frame` — первый кадр экрана загрузки, `cw:home` — первый кадр главной после
её `create()` (с этого момента она принимает нажатия). Затем «повторный визит» — тот же браузер с кэшем (второй запуск
Mini App). 3 прогона (`LOAD_RUNS`), медиана; `LOAD_JSON=файл` — сырые цифры с таймлайном запросов. Preview отдаёт те же
заголовки кэша, что Vercel (`assets/*` — навсегда, плагин `previewCacheHeaders` в vite.config.ts).

### До / после

CPU ×4, Fast 3G, медиана 3 прогонов. «До» — рабочая ветка перед пакетом (с теми же метками).

| метрика | до | после |
|---|---|---|
| первая отрисовка (FCP) | — (пустой тёмный экран до первого кадра Phaser) | **0.64 с** — HTML-заставка |
| первый кадр BootScene | 5.44 с | 5.76 с (JS и пакет картинок качаются параллельно; заставка уже видна) |
| главная готова, холодный старт | 15.50 с | **7.29 с** (−53 %) |
| главная готова, повторный визит | 11.07 с | **3.07 с** (−72 %) |
| запросов до главной | 1 JS + 85 картинок + html | 3 JS + 1 пакет + html |
| байт до главной | JS 489 КБ + картинки 504 КБ | JS 412 КБ + пакет 285 КБ (−30 %) |
| повторный визит: запросов в сеть | 86 (проверка 304 на каждую картинку) | 0 (всё хэшировано и кэшируется навсегда) |
| JS, мин. / gzip | 1 файл 1840 / 503 КБ | phaser 945 / 248 + игра 592 / 174 + рантайм 0.6 = **1538 / 423 КБ** |
| куча JS на главной (прод, после GC) | 9.1 МБ | 8.0 МБ |
| PNG в dist → что качает браузер с WebP | 2.68 МБ | **1.64 МБ** (−39 %, WebP без потерь) |

Где было время (таймлайн «до»): JS 0.6→3.9 с (канал), его выполнение до 4.5 с, затем 85 картинок по одной с RTT 562 мс по
6 соединений — до 14.6 с. То есть загрузка упиралась не в байты, а в число запросов. Повторный визит — те же 85
проверок кэша (304).

### Что сделано

- **HTML-заставка** (`index.html`, `#splash`): название, черта, бегущая полоса «Загрузка…» — те же пропорции мира 1080×1920,
  что у BootScene, без картинок и шрифтов. Видна с первой отрисовки HTML (0.6 с на 3G вместо чёрного экрана на 5+ с),
  `main.ts` плавно убирает её на первом кадре BootScene.
- **Пакет загрузки**: всё, что грузит BootScene (манифест UI без заменённых скином, значки навыков, портреты — 85 файлов),
  сборка кладёт одним файлом `assets/boot-<webp|png>-<хэш>.bin` (`assetPackPlugin` в vite.config.ts, список —
  `bootFiles` в `scripts/lib/used-assets.ts`, общий `SKIN_REPLACED` — `src/pipeline/bootAssets.ts`). BootScene качает пакет
  (полоса — по байтам, 0–90 %), режет его на `blob:`-адреса (`src/game/assetUrl.ts`, срезы одного Blob без копирования)
  и отдаёт загрузчику Phaser те же ключи, что раньше, — картинки грузятся через `<img>` без сети. Чего нет в пакете —
  грузится по одному, как раньше; пакет не загрузился — всё по одному. В dev пакета нет (`virtual:asset-pack` пустой).
  WebP-вариант пакета предзагружается из `index.html` (`<link rel=preload as=fetch>`, низкий приоритет) параллельно с JS.
- **WebP без потерь**: `npm run assets:webp` (`tools/build_webp.py`, Pillow) кодирует каждый PNG из dist в WebP lossless
  (`exact`), декодирует обратно и сравнивает RGBA — пиксель-арт пиксель-в-пиксель. Копии лежат в `assets-webp/` с sha1
  исходного PNG (`index.json`); сборка берёт копию только при совпадении sha1 — заменённый художником PNG без пересборки
  WebP просто уходит как PNG (устаревшей картинки не будет, сборка предупредит). Браузер без WebP (проверка декодированием
  картинки 1×1 до создания игры, `webpReady`) получает PNG. WebP идут в пакет загрузки, листы юнитов (`sprites.ts`) и
  анимированные эффекты боя (`ensureAnimatedFx`): листы 1.22 → 0.72 МБ, эффекты 1.01 → 0.68 МБ.
- **Урезанный Phaser** (`src/vendor/phaser-lite.cjs`, алиас `phaser` в vite.config.ts): без Arcade/Matter-физики, тайловых
  карт и плагинов Camera3D/Facebook; все игровые объекты (частицы, NineSlice, BitmapText…), звук, WebGL и запасной Canvas
  на месте. Флаги сборки (`typeof WEBGL_DEBUG` и др.) подставляет плагин `phaserFlags`. Phaser 1175 → 945 КБ.
  dev-сервер использует тот же Phaser (однократная сборка в `node_modules/.cache/phaser-lite`), так что e2e и perf гоняют
  то, что уходит в прод. `tests/phaser-lite.test.ts` падает, если код начнёт использовать вырезанное
  (`Phaser.Physics`, `this.physics`, `add.tilemap`) — тогда вернуть модуль в phaser-lite.
- **Phaser — отдельным файлом** (`codeSplitting` в vite.config.ts): после обновления игры повторный визит качает только код
  игры (174 КБ gzip), Phaser (248 КБ) — из кэша.
- **sprites.json в бандле без заметок конвейера** (`trimSpritesJson`: `source*`, `sourceFrameBboxes`, `originReconstruction`…
  читают только Node-скрипты с диска) — −65 КБ бандла.
- **Экран загрузки дешевле**: надписи полосы и имени файла перерисовываются не чаще раза в кадр (было 85 `setText` —
  перерисовка canvas и загрузка текстуры на каждый файл), картинки пакета — через `imageLoadType: HTMLImageElement`
  (без второго XHR и второго Blob в Phaser). От первого кадра BootScene до главной при тёплом кэше: 1.94 → 1.42 с (CPU ×4).

Что сознательно **не** сделано: ленивые сцены (`import()` на экран). Весь код игры — 174 КБ gzip и качается параллельно с
пакетом картинок; отдельный файл на экран добавил бы RTT (0.56 с на 3G) к первому открытию каждого экрана. Проверка
контента zod при старте тоже осталась (схемы подставляют значения по умолчанию, это часть сборки контекста).

Остаток времени холодного старта — канал: 412 КБ JS + 285 КБ пакета на 180 КБ/с ≈ 4 с, плюс выполнение JS и сборка скина.
На проде (Vercel: HTTP/2 и brotli) JS примерно на 15 % меньше, чем gzip в замере.

**Профиль боя** (CPU ×4, 12 с второго боя, dev): 88 % — `(program)`, то есть растеризация SwiftShader (заливка: фон на весь
экран, большие клетки спрайтов ×3.2, туман/свечения ADD); JS — ~10 %. Горячие места JS — в файлах эффектов боя, которые
принадлежат другому агенту, поэтому здесь только описание и предлагаемая правка:

1. **Цифры урона — `Text.setText` на каждую цифру** (`battleFx.ts FloatLayer.text` ← `number` ← `BattleScene.popNumber`):
   ~27 % всего JS боя (350 из ~1300 мс) — перерисовка canvas, `measureText`, загрузка текстуры в GPU на каждое попадание.
   Правка: при постройке сцены нарисовать в canvas строку глифов `0123456789+-КРИТ…` для каждого стиля цифр (белые,
   красные, зелёные, золотые ульты; с обводкой — тем же `TextStyleCache`), зарегистрировать как растровый шрифт
   (`Phaser.GameObjects.RetroFont.Parse` → `cache.bitmapFont.add`) и в пуле держать `BitmapText` вместо `Text`
   (`setText` тогда — только пересчёт вершин, без canvas и загрузки текстуры). Вид тот же (глифы рисует тот же шрифт).
2. **Шторка перезарядки** (`BattleScene.drawCooldown`): `Graphics` с многоугольником до 65 точек и `new Vector2` на каждую
   точку при каждом из 48 шагов, а WebGL-рендер `Graphics` триангулирует путь каждый кадр. Правка: один раз нарисовать
   48 кадров сектора в canvas-лист (`textures.addSpriteSheet`) и показывать `Image.setFrame(q)`.
3. **Плашка ульты** (`battleFx.ts showBanner`, ~106 мс за бой): `setText` имени и навыка на каждую ульту — перерисовка двух
   `Text`. Правка: кэшировать текстуры надписей по `caster|skill` (их в бою ≤ 10) или подготовить при постройке боя.
4. **Заливка** (главное на слабом GPU): обрезка пустоты листов юнитов (атлас с trim), меньше полупрозрачных слоёв на весь
   экран; опция «экономия» с плотностью холста 1.5 вместо 2 (viewport.ts) на `navigator.deviceMemory ≤ 2`.
5. **Скин при старте** (`skin.ts buildSkin`, ~0.45 с при CPU ×4): рисует все панели/кнопки в canvas и грузит в GPU до
   главной. Можно рисовать только то, что нужно главной, остальное — по первому запросу `tex()`.

**Пауза и 30 FPS** проверены по коду Phaser 3.90: `wake()` выбирает `stepLimitFPS` по `hasFpsLimit`, ограничитель копит
дельту и шагает при ≥ 30.3 мс — на 60 Гц ровно каждый второй кадр, пропущенные кадры не рисуются; `tests/game-lifecycle.test.ts`
и e2e (blur → цикл спит, часы боя стоят). Замерить 30 FPS в этом контейнере нельзя: SwiftShader и так даёт < 15 FPS.

## Утечки между боями (2026-09-27)

`npm run perf` падал: «утечка слушателей anims 72 → 96», «не собираются объекты Text / dead». Причины и исправления:

- **Слушатели anims**: выгрузка листа из LRU звала `anims.remove(key)` — Phaser только вынимает анимацию из менеджера,
  а её слушатели `pauseall`/`resumeall` остаются навсегда (+2 на анимацию при каждой выгрузке). Теперь
  `anims.get(key).destroy()` (`sprites.ts`, `unloadSheet`). После каждого боя — 48 слушателей, не растёт.
- **Text/dead**: 2-й бой мерился на середине — `scene.start('Battle')` с экрана итогов срабатывает на следующем шаге,
  и ожидание «итоги показаны» проходило сразу по ещё активному `Result`. Скрипт теперь ждёт, пока итоги уйдут.
- **Уничтоженные, но удерживаемые объекты**: сцены-синглтоны держали ссылки на объекты прошлого показа — главная
  (`blocks`, `claimBtn`, `chestText`, `chestImg`, `hintView`) и бой (`timeText`, `bossBar`); теперь забываются по
  `shutdown`. Прототипы классов Phaser (`Image.prototype` у Matter/Arcade) больше не считаются «dead».
- Итог (CPU ×4, 3 боя): живых Text/Image/Sprite/Container после каждого боя 79/38/3/5 (не растёт), удерживаемых
  уничтоженных 14 → **2** (оба — служебные), куча 28.3 / 29.6 / 29.6 МБ, `[perf] OK`.

## Жизненный цикл приложения (пакет U)

`src/game/lifecycle.ts`, подключается в `src/main.ts`.

- **Пауза, когда игру не видно**: `visibilitychange` (вкладка скрыта), `blur` окна, события Telegram WebApp
  `deactivated`/`activated` (Mini App свёрнут, страница при этом может оставаться «видимой»). На паузе цикл Phaser
  спит (`game.loop.sleep()` — без `requestAnimationFrame`, ноль работы CPU/GPU), бой и все анимации стоят.
  Причины паузы складываются: игра проснётся, когда уйдут все.
- **Без скачка времени**: при пробуждении сначала `loop.resetDelta()`, потом `wake()`; в сцене боя шаг времени
  дополнительно ограничен `MAX_FRAME_MS` = 250 мс (`clampDelta`) — после подвисания бой не «проматывается».
  e2e проверяет: `blur` → цикл спит, часы боя стоят; `focus` → +0.06 с.
- **Частота кадров 60 / 30** — в настройках (шестерёнка на главной), хранится в `localStorage` (`chronoworld.fpsCap`,
  `src/game/state.ts`). 30 — ограничитель Phaser (`fpsLimit`, `stepLimitFPS`) с интервалом 1000/30 − 3 мс (на экране
  60 Гц пропускается ровно каждый второй кадр, дрожание rAF не даёт 20 FPS); 60 — без ограничителя (частота экрана).
  Меняется на лету: цикл перезапускается, потому что функцию шага Phaser выбирает при запуске. Бой считается по
  времени, так что на 30 FPS он не замедляется.

## Отрисовка (fill rate)

Замер в том же headless-Chromium (SwiftShader, CPU без замедления), средний интервал кадра:

| что на экране | мс/кадр |
|---|---|
| главный экран | 118 |
| бой на паузе | 115 |
| бой без фона арены | 73 |
| бой без фона и без юнитов | 34 |
| пустой канвас 1080×1920 | 17 |

Фон на весь экран и спрайты юнитов (большие клетки с прозрачными полями, растянутые ×2.5) — основная заливка.
На телефоне это работа GPU, но у слабых GPU как раз мало заливки, а канвас всегда 1080×1920, даже на экране 720p.

**Фоны глав, тени, частицы (визуальная полировка).** Фоны топи и склепа (`backdrops.ts`) рисуются в canvas 720×1280
при первом показе темы (≈ 3.7 МБ видеопамяти каждый); держится не больше одного ленивого фона на вид (бой / карта),
смена темы выгружает прежний. Тени под юнитами и частицы темы (`ambient.ts`: 12 светлячков / 5 клочьев тумана +
7 огоньков / 18 пылинок + 2 отсвета факелов) — 20–30 картинок из трёх маленьких общих текстур (≈ 0.03 МБ), создаются
один раз при постройке боя, движутся в `update` без твинов. Замер `npm run perf` (CPU ×4, 3 боя, бои 1 и 3):
шаг Phaser 9.6 / 9.1 → 9.7 / 9.4 мс, JS за бой 3.06 / 2.66 → 3.12 / 2.67 с, объектов в сцене 229 → 257,
текстуры в бою 72.4 → 72.8 МБ. Самые крупные из частиц — туман топи (5 × ≈ 640×190 при alpha ≈ 0.1).
