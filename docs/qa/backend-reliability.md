# Надёжность онлайна: протокол 2

Проверено локально 04.10.2026. Production, реальные игроки, Telegram-рассылки и развёртывание не использовались.

## Исправленные случаи

1. Supabase SDK возвращал `{ data, error }`, а обработчик отвечал «успешно» при ошибке записи. Общий `checkedDatabase` теперь превращает ошибки select/count/write/RPC в отказ запроса. Клиент принимает только разобранное подтверждение записи с положительной серверной ревизией.
2. Старый запрос мог перезаписать новую игру другого устройства. `cw_save.write_revision` — отдельная серверная последовательность; `save_version` остаётся версией формата игры, `data.revision` — ревизией локального SaveSlot. Запись выполняется по CAS `expectedRevision`, не по времени телефона. Один `writeId` сохраняется вместе со снимком и используется при retry после потерянного ответа.
3. Параллельные gift/ref claim удваивали выдачу, а потерянный ответ мог уничтожить награду. RPC блокирует строку получателя, проверяет дневной лимит пяти колокольчиков, переводит ожидающие бонусы в долговечные `cw_reward_grant`. Неподтверждённые UUID выдаются повторно; клиент применяет UUID ровно один раз. ACK происходит в той транзакции, где успешно записан облачный снимок с `online.appliedGrantIds`.
4. Реферальное письмо доставлялось до выбора облачной игры и исчезало при её загрузке. Все выдачи и referral sync теперь ждут выбора. Welcome-бонус тоже хранится в журнале; старый `mail.delivered: online_ref_welcome` предотвращает повторное письмо при миграции.
5. При конфликте облако ставится на паузу, локальная игра сохраняется. Выбор облачной игры резервирует локальную. При осознанном выборе локальной игры общая история уже полученных UUID переносится без повторной выдачи потраченных наград. `cw_save_get` читает историю из серверного журнала, поэтому испорченный старый `data.online` не теряет подтверждения. SQL отклоняет снимок, который удаляет подтверждённую историю.
6. Письма, прокачка и награды раньше могли не попасть в облако до следующей победы. Теперь облако планируется после каждого commit; одновременно работает только один запрос. Commit во время запроса остаётся dirty. Сворачивание приложения обходит минутное окно и использует keepalive для подходящего размера тела.
7. Недельный MVP-рекорд ошибочно зависел от изменения пожизненного рекорда. `recordMvpAttempt(score)` получает результат каждого сыгранного боя, хранит `online.mvpWeek` в общем сохранении и использует настоящую UTC ISO-неделю. Отложенный sync старой недели не переносит результат в новую. Зачистка повторяет исторический результат и не является новым конкурентным боем: вызывающий экран должен пропускать `out.sweep`.
8. Реферальные счётчики и недельные рекорды менялись через небезопасное read/update. Один SQL RPC теперь атомарно меняет профиль, выдаёт referral/welcome и обновляет рекорды через `ON CONFLICT ... GREATEST`. Запрос старой главы также не увеличивает этап другой главы.
9. У репозитория не было полной исходной схемы `cw_*`. Добавлена безопасная baseline-миграция, RLS/права и `config.toml` для JWT-independent Telegram-аутентификации. Все три Edge Function закреплены на `@supabase/supabase-js@2.99.2` с Deno lock и отдельной проверкой типов. Telegram initData отклоняет нецелые/отрицательные IDs и даты из будущего.
10. Недельная Башня теперь также отделена от пожизненного рекорда: `online.towerWeek` изменяется только через `recordTowerProgress(floor)` после победы в реальном бою. Чтение/resume забега, вход или первое действие новой недели не переносит старый этаж. `towerBest` остаётся в профиле; `towerWeek/towerWeekId` — отдельные поля sync. Успешный бой после перехода недели учитывает достигнутый этаж продолженного забега. Новый результат 4 при прежнем рекорде 100 записывает в новую неделю именно 4.
11. Итог боя заранее рассчитан из снимка при входе в BattleScene. Фоновые online-награды и смена облачной игры теперь ждут выхода из боя, чтобы старый outcome.save не удалил новое письмо/гемы/UUID. Даже если сетевой ответ пришёл после входа в бой, выдача остаётся на сервере до безопасного экрана. Выбор облака не исчезает после прежнего 30-секундного UI retry; локальный backup выбранного облака включает уже завершённый бой.
12. Старые iOS WebView без `crypto.randomUUID` используют UUID fallback через `getRandomValues`; создание снимка происходит внутри `try/finally`, чтобы отказ не оставлял очередь облака навсегда занятой.

## Совместимость и порядок развёртывания

Существующие игроки, сохранения, pending referral и подарки сохраняются. Новые поля сохранения optional. Старые версии игры читают облако и продолжают локальную игру. Небезопасные legacy-операции без `expectedRevision` / grant protocol 2 получают HTTP409 `upgrade_required`; сервер не угадывает порядок записей и не выдаёт старому клиенту неподтверждаемые награды. Legacy-клиент может создать отсутствующее облако; его дальнейшие обновления требуют обновления игры.

Порядок: применить SQL-миграции → развернуть Edge Function → опубликовать клиент. Для существующего Supabase baseline находится раньше уже применённой bot-миграции; проверить историю и использовать обычную процедуру применения недостающих ранних миграций (`supabase db push --include-all` после ревью списка). Это не команда, которая была выполнена в данном проходе.

`pg_cron`/`pg_net` — необязательные расширения обычного PostgreSQL. Bot-миграция создаёт расписание только при их наличии; на новой Supabase-инсталляции включить расширения и повторить безопасный блок расписания. `cron_key`/bot token/service key задаются отдельно, в Git секретов нет.

## Проверки

`npm test -- tests/backend-handler.test.ts tests/online-client.test.ts tests/online-reliability.test.ts tests/online-tg.test.ts tests/online-boards.test.ts tests/online-boards-client.test.ts tests/online-bot.test.ts` — реальные HTTP-обработчики с SDK double, HMAC Telegram и контроллер клиента с моделированием сети, таймеров и смены облака. Проверяются 500/409, Unicode-лимит, CAS, UUID-дедупликация, снимок во время commit, потерянный ответ, page-hide и сериализация маркеров.

`node scripts/backend-sql.mjs` — временный PostgreSQL 17 Docker-контейнер без опубликованных портов и постоянного диска. Проверяются четыре миграции с повторным применением, сохранность прежнего игрока, CAS и идемпотентный retry, 12 параллельных gift claim, 8 referral claim, дневной лимит, потерянный ответ/ACK, чужие IDs, атомарные referral increments/high scores, независимый недельный этаж Башни и запрет RPC/table для anon/authenticated. Контейнер удаляется после прогона.

`node scripts/backend-check.mjs` — `deno check --frozen` для трёх функций. Нужен Deno 2.5+; Node-тесты обработчика используют `stripTypeScriptTypes` и требуют Node 22.13+. Веб `npm run typecheck` проверяется отдельно. CI должен запускать обе backend-проверки вместе с обычным check/build.

## Границы

Прогресс и результаты боя пока приходят от клиента. CAS/транзакции защищают надёжность и повторную выдачу, но не превращают рейтинг в серверно проверяемый PvP. Перед PvP нужен серверный расчёт/проверка матчей. Live RLS, реальные сетевые обрывы Telegram WebView и расписание уведомлений проверяются на staging при публикации.

UUID не обрезаются произвольно: это нарушило бы дедупликацию. Для многолетних сохранений нужен отдельно спроектированный компактный watermark/receipt protocol; сейчас действует существующий лимит облачного снимка 512 КиБ.
