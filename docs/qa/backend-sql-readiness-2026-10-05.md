# Готовность PostgreSQL в backend CI — 05.10.2026

В `backend:sql` readiness проверял Unix-сокет через `pg_isready` без `-h`. Официальный Docker-образ
PostgreSQL во время инициализации запускает временный сервер с `listen_addresses=''`: он принимает
Unix-сокет, завершает init-скрипты и останавливается перед окончательным TCP-сервером. Успешная
проверка этого временного процесса могла пропустить тесты в промежуток остановки и вызвать
`psql: ... .s.PGSQL.5432: No such file or directory` ещё до проверки миграций.

## Исправление

- Readiness ждёт TCP `127.0.0.1` с `pg_isready -h 127.0.0.1 -t 1`, поэтому временный сервер не
  считается готовым. Общий срок ожидания — 30 секунд, пауза между попытками не превышает 500 мс.
- `psql` использует тот же TCP-хост и `-w`; локальный тестовый пароль передаётся в окружение
  `docker exec`. Ожидания интерактивного ввода нет.
- При истечении срока добавляются состояние своего контейнера и последние 60 строк его логов,
  включая stderr. Контейнер сохраняется до `finally`, чтобы аварийный выход initdb не удалял
  диагностику. В завершении останавливается и удаляется только контейнер `cw-sql-<pid>` этого запуска.
- Повторяется только проверка готовности. SQL-записи, миграции и проверки транзакций не ретраятся;
  содержимое всех SQL assertions остаётся прежним.

## Приёмка

`tests/backend-sql-readiness.test.ts` запускает настоящий CLI через контролируемый Docker-harness:

1. Первые два опроса моделируют временный сервер, принимающий только Unix-сокет. CLI ждёт третий
   TCP-ответ, затем делает ровно один SQL-вызов на том же TCP-хосте. Harness намеренно отклоняет
   первый SQL-вызов после фиксации готовности: проверяется отсутствие ретраев мутаций и cleanup.
2. При недоступном сервере и ускоренном тестовом clock CLI доходит до срока, не вызывает SQL,
   выводит State и stderr логов, затем останавливает/удаляет свой контейнер.

Обе регрессии проходят. Они входят в обычный набор Vitest, реального Docker для unit-проверки не требуют.

Дополнительно `npm run backend:sql` успешно выполнен на настоящем PostgreSQL 17 Alpine в отдельном
контейнере с init-скриптом `select pg_sleep(3)`, который продлевает временную фазу. Пройдены все
четыре миграции с повторным применением, CAS/idempotent retry, 12 конкурентных gift claims,
8 referral claims, квота, durable ACK, конкурентная синхронизация и приватность RPC.
Контейнер и собственный тестовый образ после проверки удалены; Docker daemon не перезапускался.

Первый запуск задержанного init выявил ошибку тестовой fixture: файл из workspace с umask 600
был нечитаем пользователю postgres внутри образа. Исправлена только fixture (`COPY --chmod=644`),
после чего реальный SQL-прогон прошёл. Продовые SQL-операции и миграции по этому поводу не изменялись.

Локальные журналы проверки: `/tmp/chronoworld-night-backend-readiness-tests.log`,
`/tmp/chronoworld-night-backend-sql-real.log`, `/tmp/chronoworld-night-readiness-typecheck.log`.
Production-база и внешние Docker endpoints не использовались.
